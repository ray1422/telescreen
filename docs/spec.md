# Telescreen specification

Status: draft for v0.1.0, 2026-10-27. This file is the normative product specification. `docs/config.md` and `schema/config.schema.json` specify the config and the driver contract. `GLOSSARY.md` defines the terms. `docs/adr/` records why each decision was made. `docs/spikes.md` and `docs/hardware.md` record measured facts.

Requirement IDs (for example `FLOW-3`) are stable. Refer to them in tests, tasks, and reviews. "Must" is a requirement. "Should" is a strong recommendation. "Can" is a permission.

## 1. Purpose

Some computers share physical devices, for example one display that has video cables from more than one computer. Telescreen lets the user control these computers with one keyboard and one mouse. The user opens a portal on a computer, selects a different computer, and Telescreen switches the shared display to that computer. Then the keyboard and the mouse of the first computer control the second computer while the pointer is in the portal. The picture goes through the video cable. Telescreen does not send video.

Example setup: a MacBook with a built-in display and an external display. A Linux computer also connects to the external display. The keyboard and the mouse are on the Mac.

## 2. Scope

### 2.1 Versions

Versions follow Semantic Versioning. There is no stable release, so all versions are 0.x. In 0.x, a new feature increases the minor version, and a fix increases the patch version. From v0.600.0, the hundreds of the minor version mark a large release, and the two last digits count the small features (user, 2026-11-07). Example: v0.600.0 is the UI redesign, v0.601.0 is its first small feature, v0.601.1 is a fix, and the next large release is v0.700.0. v0.5.0 is the last version before this rule. The rule applies also below v0.600.0: v0.501.0 is the first small feature after v0.5.0, a test release of the partial UI redesign (user, 2026-11-07). v0.502.0 is the next test release, with the Qt UI on Linux and the scroll fixes (user, 2026-11-08).

v0.1.0 and v0.2.0 are internal milestones. They get no tag and no release (user, 2026-10-27). The first release is v0.3.0.

| Version | Content |
| --- | --- |
| v0.1.0 | Display handoff, confirmation prompt with the hint, and keyboard and mouse forwarding, in both directions: macOS to Linux, and Linux to macOS. |
| v0.2.0 | Text clipboard sync. It syncs only in an active, authenticated session, with no loops between the peers, and it sends nothing after the user disables it or after a disconnect. |
| v0.3.0 | Hand back, FLOW-24, the verification model, and the operation drivers (section 10; user, 2026-10-27). |
| v0.4.0 (candidate) | Separate clipboard stream: image clipboard (PNG) and texts larger than 256 KiB (CLIP-6). An image is sent only when the other peer pastes, with a "Pasting from <label>…" overlay. |
| v0.600.0 | The UI redesign (section 4.7, ADR 0012, ADR 0013): separate switch and control actions, the control request, a portal only during a session, the menu, the main window, and a native UI on each platform. |

### 2.2 Not part of v0.1.0

Video streaming, clipboard (see 2.1), file transfer, atomic switching of device groups, arbitrary remote shell commands, interception of all system keys on every OS, login screen or secure desktop control, emulated displays, game relative-mouse mode, cross-platform IME translation, shortcut remapping (for example Command+C to Ctrl+C), NAT traversal, Windows.

### 2.3 General constraints

- **GEN-1** You must not hard-code macOS, Linux, two computers, or one display. Any number of computers and displays is possible. Only some computers can connect to a given device.
- **GEN-2** A device is not always a display. Any equipment that configured operations can switch is a device.
- **GEN-3** You must not claim support for a platform, a compositor, or a shortcut that you did not test. Record each verified environment in the support matrix (section 8).
- **GEN-4** Do not make up benchmark numbers.

## 3. Peers and roles

- **PEER-1** Each computer runs the same Telescreen. Each peer can be the source and the target of sessions (ADR 0006). There is no server and no client.
- **PEER-2** Each peer listens on the `endpoint` of its computer in the config. The source dials the target.
- **PEER-3** The user selects the local computer ID. Telescreen must not guess it from the host name, also when the config has one computer. If no ID is saved, the app asks one time in the start window (UI-8), and saves the answer in the local data directory (user, 2026-11-04). The answer is not in the config, because all computers can share one config. The `--computer` argument has priority over the saved ID and is not saved. If the saved ID is not in the config, the app asks again. `telescreen forget-computer` removes the saved ID.
- **PEER-4** Each peer reads the same config format. Each peer runs only the operations of its own computer (`docs/config.md`).
- **PEER-5** `telescreen` with no argument is the same as `telescreen run`, so that a launcher can start it (user, 2026-11-04). The default config is `$XDG_CONFIG_HOME/telescreen/config.yaml`, else `~/.config/telescreen/config.yaml`, on all platforms. The `--config` argument replaces it. Telescreen does not write the config.

## 4. User flow

### 4.1 Portal and candidates

- **FLOW-1** Read and validate the config. Detect the local capabilities (input capture, injection, permissions).
- **FLOW-2** The source opens a portal when a session starts (ACT-5). The portal is not in the config. The menu, the main window, and the control window list the displays, and each candidate of a display has the actions of ACT-1 (this replaces the "Open portal" button of each display, user, 2026-11-05). The control window can be on a different display. Each display has at most one portal (user, 2026-11-07). A new portal replaces only the portal on the same display, and the session of the old portal ends. Portals on other displays stay, and each portal has its own session and target (FLOW-25). For each display, evaluate `portal-match` of the local devices. No match: tell the user. More than one match: the list shows each matching device with its own candidates, and the user selects one action. Do not use the first match silently. An action names its device (ACT-6), so the portal does not ask for a device.
- **FLOW-3** Make the candidate targets: the local `handoff` keys that are also computers with the same device `id`. Show a candidate that is offline, that has no permission, or that has no `input-target` as unavailable, with the reason.
- **FLOW-4** When the portal moves to a different display, or the display topology changes, evaluate `portal-match` again. The previous device binding and its coordinates must not continue to apply.

### 4.2 Handoff and verification

- **FLOW-5** After the user selects a target, the target resolves its local `input-target` by the shared device `id`, confirms that it can inject input, and gives an exclusive lease for that device to this session.
- **FLOW-6** The source stops any old input stream and releases all held keys and buttons. Then it runs the handoff `steps` on the source computer. When the steps succeed, the target verifies the handoff as the destination (VER-1).
- **FLOW-7** With the `prompt` verifier, the target shows the prompt on its input-target display, with the `hint` of the target computer as plain text (VER-5). The prompt of a session shows the cursor of the source, so that the user can find the pointer (user, 2026-11-07). While the session waits for the acknowledgement, the source sends `PortalCursor` as in FLOW-26, and the target draws the cursor image on the prompt. The target injects no input before FLOW-10. A hand back and "Switch display only" have no portal, so their prompt shows no cursor. The source keeps the last cursor position in the portal from the start of the session, and sends it with the `AckWanted` of the target, so that the prompt shows the cursor before the first motion. After the acknowledgement, the source sends no more positions to the prompt (Claude decides, 2026-11-07).
- **FLOW-8** When the verifier of the target asks for an acknowledgement, the user acknowledges in the portal: the acknowledgement key (Return. In v0.3.0 the key is fixed; a later version makes it configurable, user, 2026-10-27), or a click in the portal (VER-4). The source accepts it only while the target reports that its verifier waits for an acknowledgement, and the portal has the window focus. At other times the key is a normal key.
- **FLOW-9** The source suppresses the acknowledgement key and the acknowledgement click. It does not forward them. The click on the switch button must not go to the target.
- **FLOW-10** Forwarding starts only after the verifier of the target answers ok, or after the steps if the target has no `verify` (VER-2), and only if the display token of the target is still valid. The UI shows the device state that the target reports (VER-6). If the input-target display disappears while the session forwards, the target ends the session with `DisplayGone`: it releases all held input and does not run a route back (a hand back runs only on a request, HB-1). After the display is back, the user starts a new handoff (2026-10-28).
- **FLOW-21** From the handoff until the verification ends (FLOW-10, FLOW-11), the portal stays fullscreen and fixed in place, and it keeps the window focus. It cannot be switched away (user, 2026-10-27). On macOS the source suppresses the gestures and shortcuts of IN-10 and the clicks out of the portal in this time, and it activates the portal again if it loses the focus. The acknowledgement key and clicks in the portal still go to the portal. On Linux the portal inhibits the compositor shortcuts in this time. A Wayland client cannot take the focus back, so a click on a different output can still move the focus.
- **FLOW-11** If the verifier answers not ok (for example the `prompt` verifier after 60 seconds with no acknowledgement, VER-5), or the `verify` operation fails, cancel the wait. The target removes the window of its verifier. The device state is unknown (VER-6). Do not switch the video input back.
- **FLOW-12** If a handoff step fails: do not start forwarding, do not retry automatically, and do not claim a rollback. After a partial success, the device state is unknown.

### 4.3 Forwarding and end

- **FLOW-13** While forwarding, the source captures, suppresses, and forwards its input to the target by two rules. Pointer motion, buttons, scroll, and gestures follow the cursor: they go to the target while the cursor is in the portal (FLOW-20). Keys follow the keyboard focus (FLOW-22). The source must not need window focus events from the target.
- **FLOW-14** Switch of the controlled computer: the cursor can leave the portal at each time (FLOW-20), and the user can click and type on the source. This is a seamless switch (user, 2026-10-27, ADR 0003). The session has no pause state: it stays in forwarding until it ends. Only the routes of single events change. The target display does not change, and no new acknowledgement is necessary.
- **FLOW-15** Portal edges with no adjacent local display stop the pointer.
- **FLOW-20** The cursor of the source is always free: the source does not freeze or lock it, and pointer motion is never suppressed (user, 2026-10-27). Only pointer input while the cursor is in the portal area goes to the target. Each key and button up goes where its down went (IN-3).
- **FLOW-22** The keyboard focus follows clicks, as on one computer with more displays (user, 2026-10-27). Keys go to the target while the portal window has the native keyboard focus of the source, also when the cursor is out of the portal. A click in the portal gives the portal the keyboard focus. The click also goes to the target (user, 2026-10-27). The native keyboard focus of the portal window is the only source of this state (user, 2026-11-07). Each button down in the portal asks for the native focus, and does not set the state itself. On macOS the source makes Telescreen the frontmost application through Accessibility (`AXFrontmost`), from a thread that is not the main thread, and then makes the portal the key window. Keys go to the target only after the OS reports the focus. Reason: in v0.5.0 a click set the state while the portal was not the key window. Then the OS sent no later focus loss, and all keys went to the target until the session ended (user, 2026-11-07). A click on a different window of the source takes the keyboard focus away from the portal by the normal OS rules. Moving the cursor alone does not change the keyboard focus.
- **FLOW-23** At each time, at most one input field on the two computers shows the keyboard focus (user, 2026-10-27: two blinking text cursors are incorrect behavior). When the portal loses the keyboard focus, the source sends `KeyboardAway`. The target then takes the keyboard focus from its applications with a focus holder that shows nothing (UI-7). When the portal gets the keyboard focus again, the source sends `KeyboardBack` before the click that caused it. The target removes the focus holder before it injects that click. At the session end, the target removes the focus holder.
- **FLOW-25** More than one portal (user, 2026-11-07: each display can connect to a different peer). Each portal has its own session (FLOW-2). For one portal, a different portal is a different window of the source, so FLOW-13 to FLOW-23 and IN-3 apply with no new rule (user, 2026-11-07). One addition: the safety exit (IN-8) ends all sessions of the source, because it ends all suppression. Rules for the implementation (Claude decides, 2026-11-07):
  - The capture has one key router for all portals. Each forwarded key and button records its portal, so that its up event goes to that portal (IN-3). At most one portal has the keyboard focus, because the native focus is one window (FLOW-22).
  - Each portal has its own FLOW-26 state and warning.
  - While a portal waits for the confirmation (FLOW-21), the capture suppresses the clicks out of all portals and the gestures that switch Spaces. A click in a different portal that forwards goes to that portal, and the native focus can move there: the user chose that portal. A guarded portal takes the native focus back only when no portal window has it, about 100 ms after it lost the focus. Reason: two guarded portals took the focus from each other in a loop, and the Mac did not respond (hardware test, 2026-11-07).
  - The events with no portal apply to all portals: a queue overflow (IN-3) ends all sessions of the source, because the queue is shared; a loss of input (IN-13) applies to all portals.
  - The menu and the main window show one session row for each portal, with the "Hand back" of that portal (HB-3). The status glyph shows Controlling while any portal forwards. The debug state (`docs/debug-protocol.md`) lists each portal.
  - Two portals can go to the same target, on two displays (user, 2026-11-07). Each session injects on the input-target output of its own device. When the pointer goes from one portal to the other, the target moves its injector to the output of the other session, so the target pointer goes to the same physical display as the source pointer. The target has one injector, so it moves between the sessions as for two sources.
- **FLOW-26** While forwarding, the source watches whether the portal is on screen (user, 2026-11-07). On macOS the source reads `NSWindow.occlusionState`. The portal is not on screen while Mission Control is open, while a different Space is on the portal display, and while the portal is not fullscreen (UI-3). While the portal is not on screen:
  - The portal area does not count as the portal: the source forwards no input (FLOW-13). The keys stay on the source also when the portal keeps the native focus. Reason: when the portal has the focus as Mission Control opens, it keeps the focus (user, 2026-11-07). Buttons, scroll, and gestures in the portal area go to neither computer, so that a click cannot reach a source window that the user cannot see, for example the Mission Control overview on the portal display (user, 2026-11-07). Pointer motion goes to the source.
  - The source sends `PortalHidden` to the target, and `PortalShown` when the portal is on screen again. These messages are not `KeyboardAway`: a click on a different window of the source is a normal action and shows no warning.
  - The target shows a warning overlay on the input-target output of the session: a fullscreen, semi-transparent layer with the text that the portal on the source is not shown and that input is paused. It uses the window of the prompt verifier (UI-5): on Linux the layer-shell overlay. A new layer surface has an open animation on KWin, so on Linux a blank, transparent warning surface stays from the start of forwarding to the session end, and the warning only changes its content (user, 2026-11-07: the animation does not make sense for a warning). It shows at once. It takes the keyboard focus and the pointer input of the target (user, 2026-11-07, later; this replaces the rule that the warning takes no input). Reason: the warning covers the display, and when the source is stuck, the user of the target must end the session with the safety exit (IN-8). The warning shows the text "Press Escape 10 times to end the session". Other keys and clicks on the warning do nothing. On Linux, the warning surface has a full input region and exclusive keyboard interactivity while the warning shows, and an empty input region and no keyboard interactivity while it is blank. On macOS, the target makes the warning window the key window, and when the warning goes away, it activates again the app that was frontmost before (Claude decides, 2026-11-07), so that the forwarded input goes there.
  - The warning overlay shows the cursor of the source, so that the user can find the pointer and go back (user, 2026-11-07). While the cursor of the source is in the portal area, the source sends `PortalCursor` with the position in the portal (0 to 1 on each axis), and the target draws a cursor image at the same position in the overlay. When the cursor goes out of the portal area, the source sends `PortalCursor` with no position, and the target removes the cursor image. The user can see the cursor on the other displays of the source. The target does not move its own pointer (Claude decides, 2026-11-07).
  - After a Space change on the source (`NSWorkspace.activeSpaceDidChangeNotification`), if the portal is not on screen within 1 s, the source gives the portal the focus again (ADR 0003). A key window alone does not change the Space: the portal got the focus and stayed off screen (2026-11-07). macOS has no public call that changes the Space, so Telescreen prevents the cause instead (UI-13). The notification and the occlusion event can come in either order. Measured on macOS 27 (2026-11-07): opening Mission Control also sends this notification, and the portal then gets the focus with Mission Control still open.
  - When the portal is on screen again, and it had the focus when it went off screen, it takes the focus again, unless a different app is frontmost. Reason: after Mission Control closes, macOS did not give the focus back to the portal (user, 2026-11-07).
  - To give the portal the focus, the source makes the portal the key window, and then makes Telescreen the frontmost app through Accessibility (`AXFrontmost`). After that, it makes the portal the key window again on the main thread. An `AXMain` request for its own window on a different thread stopped the app (2026-11-07), because AppKit changes windows only on the main thread. Reason: when only the app becomes frontmost, macOS gives the focus to one of its windows on screen. The main window got the focus, and macOS switched the portal display to the Space of the main window, so the portal stayed off screen (user, 2026-11-07). Each portal has the title `Telescreen portal <id>`, so that tools and logs can name one portal. The id is a number that the app gives to each portal it makes, and the app never gives the same id twice while it runs. A session id does not name a portal, although a portal has exactly one session (ACT-5): the target gives the session id in `SessionGranted`, after the portal opens, and two targets can give the same id. Thus this also works with more than one portal on one display (user, 2026-11-07).
  - Measured on macOS (2026-11-07): when Mission Control opens, the portal leaves the screen (`kCGWindowIsOnscreen`) and loses the key window in about 0.1 s. Not measured: whether `occlusionState` changes at the same time (AC-51). The Dock adds no window for Mission Control, so the source does not detect Mission Control itself.
  - At the start of forwarding, the source gives the capture and the target the current focus and visibility of the portal, because the window layer reports only changes (FLOW-22).
  - Linux as the source: not specified. A Wayland client cannot reliably find out whether its window is shown.
- **FLOW-16** These events end the session: a hand back (HB-1), the safety exit, a disconnect (heartbeat timeout or a closed connection), "Disconnect" on the target, "Control from here" on the target (FLOW-17), lease expiry, removal of the portal display, and revocation of a permission. Then the source stops suppression and restores the key state. The target releases all held keys and buttons. If the device state is not confirmed, show it as unknown. Do not claim an automatic recovery.
- **FLOW-17** The target shows "Controlled by <source label>" with three actions (user, 2026-10-27): "Hand back" (the main action, HB-2), "Control from here", and "Disconnect". "Disconnect" ends the session with no switch. "Control from here" ends the session, then starts a session in the other direction, with this computer as the source: a new connection that replaces the old one.
- **FLOW-18** Only a hand back (section 4.6) switches the device back. The other ends of FLOW-16 do not switch the video input. A different switch needs an explicit handoff route.
- **FLOW-24** When a computer grants a session as the target, it closes its own portal on the input-target display of that session (user, 2026-10-27). Then the display does not show two portals, and the user knows which computer is the target. Portals on other displays stay open. If the closed portal is in a session as a source, that session ends as for each closed portal. There is no special rule for three or more computers, and nobody confirms this end (user, 2026-10-27). Example: A has a portal on display D, and it is the source of a session to C. The user switches D to B by hand, and requests a session to A from B's portal on D. A grants it and closes its portal on D, so the session A to C ends. There is no nested forwarding. The control window of A shows "Session ended: <B> took this display" (user, 2026-10-27).
  - With two computers, B is C. Then the request has the same result as "Control from here" (FLOW-17): the old session ends, and the new session starts.
- **FLOW-19** If the portal display disappears from the source, stop forwarding and restore the UI. Do not continue to suppress input in a window that moved to a different display.

### 4.4 Text clipboard (v0.2.0)

- **CLIP-1** Text clipboard sync is on by default (user, 2026-10-27). Reason: the sync works only in a session that the user started, and Telescreen does not keep the texts. The config key `clipboard.text` of each computer gives the start value (default `true`). The control window has a switch that changes it while the app runs (user, 2026-10-27). The switch is not saved.
- **CLIP-2** The sync works in both directions (user, 2026-10-27), only while a session is in forwarding, and only on the authenticated connection of that session. A peer sends its text only while its own switch is on. A peer applies a received text only while its own switch is on.
- **CLIP-3** A peer sends its clipboard text when the local clipboard changes during the session. It does not send the text that was on the clipboard before the session started (user, 2026-10-27). Reason: privacy. A text from before the session can be old, and the user did not copy it for this session.
- **CLIP-4** No loops: a peer does not send back a text that it set from the other peer.
- **CLIP-5** After the switch goes off, after the session ends, or after a disconnect, a peer sends nothing. It does not send a change from that time later.
- **CLIP-6** Only plain UTF-8 text. A text larger than 256 KiB is not sent, and the source shows a notice (user, 2026-10-27). Reason: the text uses the same reliable stream as the input events, and a large text delays the keys after it. A later milestone sends larger texts on a separate clipboard stream.
- **CLIP-7** A password manager can mark a clipboard item as concealed (macOS `org.nspasteboard.ConcealedType`; Linux `x-kde-passwordManagerHint` with the value `secret`). A peer sends a concealed item as other text, with the concealed mark (user, 2026-10-27). The receiving peer sets the same mark on its own clipboard, so that clipboard history tools do not record the item. When the concealed item goes off the clipboard of the sending peer (for example, the password manager clears it), the sending peer tells the other peer. The other peer then clears its clipboard if it still holds that item. All of this is best effort (user, 2026-10-27): each OS and each clipboard tool keeps its own limits, and Telescreen does not remove them. For example, some password managers on Linux do not set the mark; their items sync as other text. On Wayland, the clipboard also becomes empty when the program that copied quits; the sending peer cannot tell this from a clear, and does the same. Not verified: whether clipboard history tools on Linux other than KDE obey the mark, and whether macOS Universal Clipboard obeys it.
- **CLIP-9** No log and no debug output contains clipboard text (user, 2026-10-27).
- **CLIP-10** A paste on the receiving peer needs no extra authentication (user, 2026-10-27). Reason: the peers are paired (ADR 0004), and the user confirmed the session at the prompt. Also, a pushed text is already on the local clipboard, so Telescreen cannot see the paste.
- **CLIP-11** When the session ends, for each cause, a peer clears its clipboard if it still holds a text that it set from the other peer (user, 2026-10-27). This includes texts with no concealed mark. Reason: the connection ends, and the text must not stay. The peer does the same when its switch goes off (Claude decides, delegated by the user, 2026-10-27). This is local: the peer sends nothing (CLIP-5). If the app stops unexpectedly, the peer cannot clear. On Wayland, the text also goes off the clipboard when Telescreen quits, because Telescreen provides it.
- **CLIP-12** Only the clipboard selection syncs. The Linux primary selection (select and middle-click paste) does not sync (Claude decides, delegated by the user, 2026-10-27). Reason: macOS has no primary selection.
- **CLIP-8** The clipboard is a platform capability behind an interface. macOS uses `NSPasteboard`. Linux uses the data-control protocol on its own Wayland connection. Linux uses `ext-data-control-v1` (user, 2026-11-04). KWin has only this protocol, and niri and Hyprland also have it. If the compositor does not have it (for example GNOME), the capability is missing. Then the control window does not show the switch, and it shows a notice with the cause from the start (Claude decides, delegated by the user, 2026-10-27). The input callbacks never read the clipboard (IN-2).

### 4.5 Verification (v0.3.0)

ADR 0009. The **destination** is the computer that a handoff switches the device to.

- **VER-1** `verify` is in the device section of the destination. The destination runs it after the steps of each handoff to it, also of a hand back. A handoff route has no `verify`. The computer that runs the steps tells the destination over the network when the steps succeed.
- **VER-2** No `verify` means no check (user, 2026-10-27). Forwarding starts when the steps succeed, and the device state is unverified.
- **VER-3** A verifier talks with the core in JSON lines (`docs/config.md`). It can show text on the switched display (`{"show":…}`) and ask for an acknowledgement of the user (`{"want":"ack"}`). The core answers `{"ack":true}` when the user acknowledges. The verifier answers ok or not ok. It does not know how the user acknowledged. The purpose is to make sure that a user sees the switched display (user, 2026-10-27).
- **VER-4** The core decides which user actions are an acknowledgement (user, 2026-10-27). If the computer that started the handoff has a portal: Return, or a click in that portal, sent over the network (FLOW-8). Else, on the destination: Return in a window of Telescreen on the destination, or a click in the window of the verifier or in the portal (user, 2026-10-27). A click in the control window is not an acknowledgement, because it can hit a button (user, 2026-10-27). A hand back always uses the actions on the destination, also when the source requested it: the session already ended, and the user then uses the keyboard of the destination. On macOS and on Linux the window of the verifier then takes clicks and the keyboard focus, because the portal can be closed with its session (ACT-5; Return and clicks did nothing, user, 2026-11-07). On Linux the layer-shell prompt then has a full input region and takes the keyboard. A click in the window of a verifier acknowledges only the verification of that window. Return in a window of Telescreen acknowledges the verification of that window, else the first verification on this destination that waits (Claude decides, 2026-11-07).
- **VER-5** The built-in `prompt` verifier shows the prompt with the `hint` of the destination in its own window on the switched display (UI-5), asks for an acknowledgement, and answers ok. After 60 seconds with no acknowledgement (fixed in v0.3.0), it answers not ok. If the window cannot show, it answers not ok at once (FLOW-11). This includes a window that the window layer reports as failed after the show, and a target session then ends with `VerifyFailed` (Claude decides, 2026-11-07). It does not use the portal, because the portal can be gone.
- **VER-6** The device state is per device on the destination, and it does not depend on a session: confirmed (the verifier answered ok), unverified (no `verify`), or unknown (a failed or timed-out verification, or a partial handoff). After a hand back, the computer that ran its route back changes its own state: a success sets "no state" (the device is not on this computer), and a partial failure sets unknown. A failure with no completed step does not change the state (user, 2026-10-27). For an unknown device, the device list shows "It is back". The user presses it to set the state to confirmed. The source of a session shows the state that the target reports (UI-4).
- **VER-7** The protocol has no other user input. A verifier that needs other input (for example the state of a Bluetooth keyboard) reads it itself on the destination (user, 2026-10-27).
- **VER-8** A display shows one verification prompt (user, 2026-11-07). When a verification shows its prompt on a display, each earlier verification with a prompt on the same display stops, as for a verifier that answers not ok (FLOW-11): its prompt goes away, and the device state is unknown. A target session that verifies then ends with `VerifyFailed`. The warning of FLOW-26 is not a verification prompt.

### 4.6 Hand back (v0.3.0)

- **HB-1** A hand back switches the device of a session back to the source (user, 2026-10-27). It is not a special flow, but three steps: the session ends as for "Disconnect"; the target runs its own `handoff.<source>` route for the device, as a handoff with no portal and no forwarding; then the source verifies as the destination (VER-1). It covers one device: the device of the session. FLOW-12 applies to the steps.
- **HB-2** On the target, each incoming session has "Hand back" as the main action (FLOW-17), in the control window and in the menu of the status icon (UI-4). If the target has no `handoff.<source>` route for the device, the action stays in its place, is disabled, and shows the cause, for example "No route back to <source> in this config" (user, 2026-10-27).
- **HB-3** The source can also start a hand back (ADR 0010): it sends a request, and the target runs its own `handoff.<source>` route. Only the source of an active, authenticated session can request it, and it causes only the route back to the source. The trigger on the source is "Hand back" in the session row of a portal, in the menu and in the main window (UI-9, FLOW-25). It requests the hand back of that portal only. The source has no hand back shortcut (IN-7), and a portal that leaves fullscreen does not request a hand back (UI-3) (user, 2026-11-07).
- **HB-4** If the target has no route back when the source requests a hand back, the session ends, and the target shows a notice that the user must switch the display by hand. The target shows it, because the display shows the target. The source adds the same notice to its control window.
- **HB-5** The safety exit (IN-8) only ends the session. It does not start a hand back.

### 4.7 UI redesign

ADR 0012 and ADR 0013 (user, 2026-11-06). This section replaces some current rules when the redesign is implemented. Until then, the current rules apply. Each replaced rule names its replacement. In this section, "the menu" is the panel of UI-9, and "the main window" is the window of UI-12. The main window replaces the control window: when the redesign is implemented, "control window" in this spec means the main window.

Actions:

- **ACT-1** Each candidate of a display has three actions (ADR 0013):
  - "Switch & control": the handoff and a session, by FLOW-5 to FLOW-12.
  - "Switch display only": the handoff with no session. FLOW-6 and FLOW-12 apply to the steps. The destination does not need to run Telescreen.
  - "Control only": an attach (ACT-3).
- **ACT-2** After "Switch display only", the destination verifies by VER-1 if it is reachable. The acknowledgement is on the destination, as for a hand back (VER-4), because no session and no portal exist. If the destination is not reachable, nobody verifies, and the source shows "switched, not verified" (Claude decides, 2026-11-06).
- **ACT-3** An attach is a session with no handoff steps, for a device that already shows the target. The target grants the lease by FLOW-5 and verifies by VER-1, as after the steps of a handoff (user, 2026-11-06). The acknowledgement follows VER-4 and FLOW-8. Then forwarding starts by FLOW-10. A candidate that is offline cannot attach, and the menu shows the reason (FLOW-3).
- **ACT-4** Control request: a peer can ask a different peer to control it on a device (ADR 0013). The label on the asking peer is "Let <peer> control this display". The request names only the device id. The receiving peer evaluates `portal-match` for that device id. It opens a portal on the matching display, and it attaches to the asking peer (ACT-3). It does not ask its user first (user, 2026-11-06). Reason: its display can show the asking peer at that time, so its user cannot see a question. The acknowledgement on the keyboard of the receiving peer is the consent.
  - Only a paired, authenticated peer can send a control request.
  - While the receiving peer waits for the acknowledgement, FLOW-21 applies. Its user ends the wait with the safety exit (IN-8), or the prompt times out (VER-5).
  - If the receiving peer has no matching display, has no capture permission, or already has a session as the source on that display, it refuses the request. The asking peer shows the reason (Claude decides, 2026-11-06).
- **ACT-5** The portal exists only while a session exists on the source. The source opens it when a session starts, before the handoff steps, so that FLOW-21 applies. It closes the portal when the session ends. This replaces "Open portal" in FLOW-2: the menu and the main window list the displays, and FLOW-2 to FLOW-4 apply to that list. The portal shows no candidates. It shows at most one status line. Each portal closes with its session, also the portal of "Control from here" (FLOW-17). When the portal closes, its status line goes away. Thus a session end that the user did not make on this computer ("End session", "Hand back") adds a notice with the reason, for example "The session with Linux ended: connection lost.", and "The display state is unknown." if it is unknown (FLOW-16) (Claude decides, 2026-11-07).
- **ACT-6** Rules for the implementation of ACT-1 to ACT-5 (Claude decides, 2026-11-07):
  - Each action names the display, the device id, and the target. The menu knows the device from the `portal-match` result of each display. The portal does not choose a device.
  - An attach needs the same route as a handoff: the source has `handoff.<target>` for the device, and the target refuses with `NoRoute` by NET-4 if it does not. The wire has no separate attach request: the source sends `RequestSession`, and after `SessionGranted` it sends `HandoffDone` at once with no steps.
  - The device state after an attach: `confirmed` if the target verified, else `switched, not verified`, because the user switched the display by hand. At the end of the session, `switched, not verified` becomes `unknown`, as after a handoff (FLOW-16).
  - "Switch display only" needs a route and nothing more. It works when the destination is offline and when the source has no capture or suppress permission. It makes no session and no portal, and it does not arm the capture. It runs the same `handoff.<target>.steps` as "Switch & control". The `portal` field of the driver request describes the chosen display, with no portal window.
  - After the steps of "Switch display only", the source sends `DisplaySwitched { device }` if the destination is connected. The destination accepts it only if the config of the sender has `handoff.<destination>` for the device (NET-4). Else it ignores the message. When it accepts, it ends its sessions of that device in both roles (FLOW-6), and it verifies as after a hand back (HB-1, VER-4). The source changes its own device state by VER-6, as the computer that ran a route back. If the destination is not connected, the source shows the notice "Switched to <target>, not verified: <target> is not connected". The source does not dial for this message.
  - The receiving peer of a control request refuses with `ControlRefused { device, reason }`. The reasons: the device is unknown; the receiving peer has no `handoff.<asking peer>` route for the device; no display matches; more than one display matches; `portal-match` failed on a display (AC-9); the receiving peer cannot capture or suppress; it already has a session as the source on the matching display (FLOW-2; a session on a different display does not count). It does not guess between two matching displays.
  - "Let <peer> control this display" dials the peer if it is not connected, and sends the request when it connects. The asking peer shows "Waiting for <peer>" until the attach `RequestSession` of that peer for that device arrives, until `ControlRefused` arrives, or for 15 seconds. After 15 seconds it shows "<peer> did not answer".
  - The wire protocol version is 6.

Telescreen ignores other `telescreen:` URLs.

- **UI-11** Linux entry points:

The property `Menu` (type `s`) is the `MenuScreen` as JSON (UI-18). When the value changes, Telescreen sends `PropertiesChanged` with the new value. The method `Send(s)` takes one `Intent` as JSON. The methods `ShowMainWindow()`, `OpenSettings()`, and `Quit()` have no arguments. UI-15 uses the same bus name for the single instance.

Before the app starts (the start window of UI-8), `Menu` is empty, `ShowMainWindow()` does nothing because the main window opens when the app starts, and the other methods reply with `org.freedesktop.DBus.Error.Failed` (Claude decides, 2026-11-07).

The first button is the primary action of UI-18 and has the accent color. An unavailable action has no button: the popup is narrow, and "Control only" is unavailable in most states. If "Switch & control" is unavailable for an online candidate, the status line shows its reason (Claude decides, 2026-11-07). The main window shows each unavailable action with its reason in the overflow menu.

- **UI-18** The view model of the menu (Claude decides, 2026-11-07):
  - It is one serializable value (`MenuScreen`), the same on all platforms. The KDE applet reads it over D-Bus as JSON. Intents come back as JSON too.

A display with no matching device is last. Displays with the same order keep the order of the platform (user, 2026-11-07: the order of the config shows the real arrangement; the platform list had the built-in display first).

This evaluation dials the candidates of each matching device, as a portal does (NET-10). "Refresh" does not evaluate `portal-match` again: it only dials (NET-10, user, 2026-11-07).

The subtitle always shows the status and the primary action, for example "Online · Switch & control", because a touch screen has no hover. While the request waits, the row subtitle shows "Waiting for <peer>…".

- **UI-13** The main window opens when the user starts Telescreen, and when the user starts it again while it runs. It shows the content of the menu, the computers and their trust state, the device states with "It is back" (VER-6), and the notices. It has the start window of UI-8 when no computer is selected.

The exception is a window that shows on each Space and over a fullscreen window (`canJoinAllSpaces` and `fullScreenAuxiliary`), because macOS does not change the Space for it: the prompt (UI-5) and the menu (UI-9). The main window is not such a window: when it is on a display with a portal, also after the user moves it there (for example in Mission Control), it goes to the Dock (minimize; user, 2026-11-07). First it moves to the center of a display with no portal, if there is one, so that it comes back there from the Dock. When no portal is open, a main window that Telescreen minimized comes back (user, 2026-11-07: after the session it must come back). ### 4.8 Pairing (a v0.6XX.0 version, number not decided)

ADR 0014. A side discussion with the user (2026-11-07) gave this design. It replaces the typed fingerprint of ADR 0004 for normal use. `telescreen trust` stays as the fallback. Do not put pairing in v0.600.0 without a question to the user. The implementation is not scheduled.

- **PAIR-1** Pairing has a GUI and a CLI (user). Both use the same flow. On B, the user can use the CLI, for example over SSH from A, so that the display does not need to show B before Telescreen runs (user).
- **PAIR-2** Each side needs one human action, and the user does not type (user). A must confirm (user). The steps:
  - On A: the user selects "Pair a computer…" (one click).
  - On B: the user selects A from the list (one click). B shows a 6-digit code.
  - On A: Telescreen shows 3 codes and no "Accept" button. The user selects the code that B shows (one click). Reason: if the user did not start pairing on B, B shows no code, so the user cannot accept a request blindly. A PIN alone is not sufficient: a person who sees the PIN can send a request first (user).
- **PAIR-3** Discovery (Claude decides, 2026-11-07, unless the statement names the user):
  - Pairing mode on A lasts 2 minutes. A opens a temporary port, not the main endpoint. It registers an mDNS service with a random instance name, as NET-14.
  - The record is not trusted. It only lets B find A.
  - A shows no pairing request unless the user started pairing mode on A.
  - The host name in the record and the fact that the computer is pairing are not private data (user).
- **PAIR-4** Protocol: numeric comparison with a commitment, with no PIN (Claude decides, 2026-11-07):
  - The connection uses the long-term keys of both peers.
  - A sends C = H(fpA, fpB, nA). B sends nB. Then A sends nA.
  - Both compute SAS = H(fpA, fpB, nA, nB), truncated to 6 digits. The SAS binds the fingerprints that the connection uses and that go into the trust list.
  - An attacker in the middle has 1 chance in 10^6 for each attempt, and the user sees a failed attempt.
- **PAIR-5** Rules (Claude decides, 2026-11-07):
  - A handles one request at a time. If a second connection arrives in the pairing time, A stops all of them and shows "Another computer also tried to pair".
  - B shows a warning if more than one computer is pairing.
  - The computer id of the peer comes from the authenticated channel. It must be in the local config.
  - If the trust list already has a fingerprint for that id, pairing refuses and tells the user to remove the old fingerprint first. It does not replace it.
  - Each peer writes the trust list only after the local confirmation and the confirmation of the peer. If the connection drops after one peer wrote, the result is harmless, because mutual TLS needs both entries (NET-3). Telescreen shows "Pairing not complete".
  - The messages have a size limit. The temporary port closes when pairing ends.
- **PAIR-6** CLI (Claude decides, 2026-11-07): `telescreen pair` runs the same flow as the GUI. It reads the local identity and writes the trust list, so the app does not need to run. If the app runs, the command tells it to read the trust list again.
- **PAIR-7** This is not trust on first use, because the user compares the code. `telescreen trust` stays as the manual fallback (ADR 0004).
- **PAIR-8** Open:
  - The version number.
  - When mDNS does not work: can B give the address of A (for example `--host`)?
  - A PIN as an option.

## 5. Input

- **IN-1** Capture, suppress, forward, and inject are four separate capabilities. Detect and report each one. Window key events and global hotkey registration are not input capture.
- **IN-2** Input callbacks (event taps, Wayland input events) only capture, decide to suppress, and push to a bounded queue. They must not run helpers, wait for the network, or block the UI.
- **IN-3** Key and button down/up events must stay in pairs. Pointer motion can be merged. Key and button events must not be dropped. If the queue overflows, end the session and release all held state.
- **IN-4** Both peers release all held keys and buttons on a session end. The target must release them on a heartbeat timeout by itself; it must not wait for key-up events from the source.
- **IN-5** Keys go by physical key identity, not by the character. The input method of the source must not change the key (spike 1). Modifier keys go by physical key: Command to Super, Option to Alt, Control to Control.
- **IN-6** Do not remap shortcuts. The `hint` tells the user the shortcuts of the target.
- **IN-7** Removed (user, 2026-11-07). Telescreen has no hand back shortcut. The source requests a hand back only from the session row of a portal (HB-3). The only key sequence that Telescreen handles itself is the safety exit (IN-8).
- **IN-8** The safety exit (Escape 10 times in 5 seconds) ends suppression and the session, with no hand back (HB-5). The input callback counts the presses itself, with no dependency on the main thread, the UI, or the network. It counts each press while forwarding, also when the key is not forwarded, for example when the portal does not have the keyboard focus or is not on screen (FLOW-26; the safety exit did not work then, user, 2026-11-07). It counts each press also while a portal waits for the confirmation (FLOW-21), because then the input can be stuck too (user, 2026-11-07, after the hardware test). Escape is still forwarded when the portal has the keyboard focus. It counts only while a portal waits for the confirmation or forwards, because only then does the source suppress input (user, 2026-11-07). An armed capture with no such portal does not count. It does not count an auto-repeated key down (macOS: `kCGKeyboardEventAutorepeat`; Linux: a key event with the value 2), because a held key is not ten presses (user, 2026-11-07). The Linux portal window gets its keys from winit on Wayland, and winit makes the key repeats itself; a repeat has `KeyEvent::repeat` set, and this flag stands for the value 2 (Claude decides, 2026-11-07). All capture code applies these rules through one shared function in `telescreen-core` (Claude decides, 2026-11-07).
  - The destination also has the safety exit while it shows the warning of FLOW-26, because the warning has the keyboard focus (user, 2026-11-07). The warning window counts Escape by the same rules. Then the destination ends each session that shows the warning, with `SafetyExit` and no hand back (HB-5). It releases all held input (IN-4). The destination has one counter for all of its warnings, and the main loop counts the presses with its own clock, because the warning window gets its keys from the window layer, not from an input callback. The destination sends `End` with the reason `SafetyExit` to the source, the same reason as for the safety exit on the source, so the wire protocol does not change (Claude decides, 2026-11-07).
- **IN-9** A watchdog that is independent of input events must stop suppression when the main loop does not respond for a few seconds, and when a suppression deadline passes (spike 2).
- **IN-10** While forwarding on macOS, suppress all gestures and shortcuts that switch Spaces or applications, or that open Mission Control, by the rules of FLOW-13: shortcuts while the portal has the keyboard focus, and gestures while the cursor is in the portal. Do not forward gestures (ADR 0003). At other times, they go to macOS.
- **IN-11** Pointer position: the source maps the pointer position in the portal, normalized to the portal size, to the input-target display of the target. The backends handle scale, rotation, negative origins, and pixel coordinates. The pointer must not leave the input-target display on the target.
- **IN-14** The target multiplies each forwarded scroll by the `scroll-speed` of its own computer section (`docs/config.md`). The default is 1. The value applies only to forwarded scrolls: local input of the target does not change. Reason: the correct speed depends on the applications and on the compositor of the target (user, 2026-11-04). A target that can inject only whole pixels keeps the remainder for the next scroll, so that a slow scroll does not get lost.
- **IN-15** On Linux, the pointer injection does not need the wlroots virtual pointer (user, 2026-11-04). If the compositor has `zwlr_virtual_pointer_manager_v1` (niri), the injector uses it. Else the injector makes a uinput absolute pointer (KWin). The compositor maps the range of that device to all outputs together, so the injector computes the position from the logical bounds of the outputs, for each motion. Its scroll has two forms (user, 2026-11-05; spike 5):
  - On KWin, unless the quirk `kwin-button-scroll` is off (IN-16), the injector uses a second uinput device with button scroll, because applications animate a wheel scroll and KWin sends a different scroll source only from a libinput device. The source of this scroll is `continuous`. The middle button of this device stays down from the start of a session. No client sees this button. The injector presses it again at the start of each session. It lets the button go up only after a motion of the device, so that libinput sends no click. The injector sets the KWin scroll factor of this device (KWin stores it in `kcminputrc`). KWin shows a scroll cursor for a device with button scroll on. Thus while the button is down, the injector turns off the KWin setting for button scroll: libinput applies this change only after the button goes up, so the scroll continues and the cursor does not change. Before each button down, the injector turns on the setting and reads it back. If KWin does not confirm it, the injector does not press the button and uses the wheel scroll.
  - On each other compositor, and if the quirk is off, the scroll is a wheel scroll with high-resolution values. Reason: the button scroll was tested only on KWin.
  - On both forms, 60 logical pixels of a scroll are one wheel notch. Thus `scroll-speed` (IN-14) has the same effect on both forms.
  - A scroll target in Chromium stays until the button goes up, and a new press of the button can leave Chromium in a scroll that does not move until a key (seen on the hardware, 2026-11-08). A wheel scroll releases the target (IN-18). Thus at the end of each button scroll (IN-18: at `end`, and 300 ms after the last scroll event), after a finger scroll (not a wheel scroll), the injector sends one high-resolution wheel unit (about 1 pixel, spike 5) on the absolute pointer, on the other axis than the last scroll, and then the opposite unit as a separate event (user, 2026-11-08). Thus the view does not move: most panes cannot scroll on that axis, and the two units cancel (with one unit on the axis of the scroll, the view moved 1 pixel at each end). Then the next scroll goes to the pane below the pointer. The unit is not sent at `begin`: Chrome animates a wheel scroll, and the first scroll then came late (user, 2026-11-08). The button stays down for the whole session: the button scroll has no end. Ends at a click, at a pointer motion, and after an idle time of 1 s were tested and removed: they did not release the target, or they made the scroll stop (user, 2026-11-08). A virtual touchpad, which ends each gesture, is not used (spike 10).
  - Limit: if a VT change or a compositor restart occurs during a session, libinput can lose the button state. Then a scroll can move the pointer until the next session starts.
- **IN-16** A quirk is a platform workaround with a name (user, 2026-11-05). Each quirk is on by default. The `disabled-quirks` list in the computer section (`docs/config.md`) turns off a quirk on that computer. Thus the user can turn off a workaround that fails after an update of the platform, with no new build. The quirk of IN-15 is `kwin-button-scroll`.
- **IN-17** On macOS, the source suppresses each button that goes to the target (user, 2026-11-07). Thus a click in the portal area cannot reach a source window that the user cannot see, for example the Mission Control overview on the portal display. The portal gets the native focus by FLOW-22, not from the click.
- **IN-18** Each forwarded scroll has an end (user, 2026-11-07). A toolkit of the target can lock a scroll to one widget until the scroll ends. A scroll with no end then stops in that application until the next end (seen in Claude desktop, a Chromium application, on KWin; a wheel scroll on the target released it). Each scroll event on the wire has a phase: `begin`, `update`, `end`, or none (a wheel). The macOS source takes the phase from the trackpad, and the end comes after the momentum. The end of the finger contact is not `end`, because momentum can follow. The target ends the scroll at `end`, and 300 ms after the last scroll event that is not `end`. The wlroots virtual pointer sends `axis_stop`. The button scroll of IN-15 does not let the button go up at an end: a new press waits 250 ms (with an end at each `end`, the scroll was choppy, user, 2026-11-07). One wheel unit releases the scroll target instead. Each new session and each disconnect also lets the button go up.
- **IN-19** The Linux target smooths each finger scroll (a scroll with a phase, IN-18), because the network can delay scroll events and then give several together (user, 2026-11-08). It uses no time stamps from the source and no fixed delay. The first event of a scroll (no scroll event in the 100 ms before it) goes at once. Later events add their distance to a distance that waits. While distance waits, the injector injects a part of it each 8 ms: the average speed of the scroll events for that time, and at least the part that injects all of it in 50 ms. Events less than 2 ms apart came together and do not change the speed. It never injects more distance than it received. A new scroll event cancels an `end` that waits. A wheel scroll goes at once, after the distance that waits. The end of a scroll (IN-15, IN-18) waits until all distance is injected. At the end of a session, the distance that waits is dropped. While distance waits, the main loop runs the timer of the injector each 8 ms, else each 100 ms (Claude decides, 2026-11-08).
- **IN-20** Special keys on a macOS source (user, 2026-11-09). A special key is a key that macOS reports as a system-defined event (`NSEventTypeSystemDefined`, subtype 8), not as a key event. The `special-keys` key of the source computer section (`docs/config.md`) selects what each group does. The source decides; the target has no setting, because the user can want a key on the source for a special use, or keep the media keys on the source by habit (user, 2026-11-09).
  - The groups and their keys, with the evdev key that the source forwards (`NX_KEYTYPE_*` in `IOKit/hidsystem/ev_keymap.h`):
    - `brightness`: `BRIGHTNESS_UP` (2) to `KEY_BRIGHTNESSUP`, `BRIGHTNESS_DOWN` (3) to `KEY_BRIGHTNESSDOWN`.
    - `volume`: `SOUND_UP` (0) to `KEY_VOLUMEUP`, `SOUND_DOWN` (1) to `KEY_VOLUMEDOWN`, `MUTE` (7) to `KEY_MUTE`.
    - `media`: `PLAY` (16) to `KEY_PLAYPAUSE`, `NEXT` (17) and `FAST` (19) to `KEY_NEXTSONG`, `PREVIOUS` (18) and `REWIND` (20) to `KEY_PREVIOUSSONG`.
    - `keyboard-light`: `ILLUMINATION_UP` (21) to `KEY_KBDILLUMUP`, `ILLUMINATION_DOWN` (22) to `KEY_KBDILLUMDOWN`, `ILLUMINATION_TOGGLE` (23) to `KEY_KBDILLUMTOGGLE`.
  - `FAST` and `REWIND` go to the next and previous track, because the Apple keyboard sends them for its F9 and F7 keys, the keys show the next and previous track, and the desktops on Linux bind `XF86AudioNext` and `XF86AudioPrev`, not the fast forward keys (measured on the MacBook of the user, 2026-11-09; user, 2026-11-09). Thus a held key does not seek on the target.
  - While a forwarding portal has the keyboard focus (FLOW-13), the source handles each special key of a group by its list: a group in `send-to-target` goes to the target (the source sends the key down at the first key down and the key up at the key up, and suppresses the event on the source); a group in `keep-on-source` goes to macOS on the source and not to the target; a group in neither list goes to neither computer (the source suppresses the event and does not forward it). The default is neither list for all groups, the behavior before IN-20. The names of the lists tell that they are rules of the source (user, 2026-11-09).
  - The source does not forward an auto-repeated key down (bit 0 of `data1`), so that a held key is one press on the target (Claude decides, 2026-11-09). The key down and up stay in pairs (IN-3).
  - Each other system-defined event, also the other `NX_KEYTYPE_*` keys (for example the power key and Caps Lock), keeps the behavior of IN-10: suppress, do not forward.
  - While no forwarding portal has the keyboard focus, each special key goes to macOS.
  - The key codes in this list are standard on Linux: xkeyboard-config maps them to the `XF86*` keysyms, and KDE Plasma binds them. Other compositors, for example niri, need a binding in their own config.
  - The source reads the subtype and `data1` from the CGEvent fields 83 and 149. They are not public; they were measured on macOS 27 for each special key and Caps Lock (2026-11-09). The source does not use `+[NSEvent eventWithCGEvent:]`: on the event tap thread, AppKit asserts the main queue for a Caps Lock event and the process stops (seen on the hardware, 2026-11-09).
  - Limits: a Linux source does not use `special-keys`; it forwards the keys that its portal window gets. A macOS target does not inject these keys, because it injects only key events with a `kVK_*` code.
- **IN-12** If the OS blocks capture (for example macOS Secure Event Input, or a missing permission), report it clearly. Do not claim that capture works.
- **IN-13** Input lost: if the capture can no longer see the up events of the forwarded keys, the source releases all held state of the session and sends `ReleaseAll`. The session continues. Examples: the Linux portal loses the keyboard focus (other windows get the up events), macOS turns on Secure Event Input during the session, and macOS disables the event tap for a time.

## 6. Portal window and prompt

- **UI-1** The portal is borderless and covers its display. On macOS it is a native fullscreen Space, above the menu bar level (window level 26), so the menu bar and the title bar do not show at the top edge (ADR 0003, spike 1).
- **UI-2** While the portal has the focus, it allows only Roman input sources, and macOS restores the previous input source after it (spike 1).
- **UI-3** If the portal leaves fullscreen while its session forwards (for example a drag out of its Space in Mission Control), detect it. Then the portal is not on screen by FLOW-26: the source forwards no input, and the target shows the warning with the cursor of the source. The source does not request a hand back, and it does not make the portal fullscreen again (user, 2026-11-07). The portal stays a fullscreen window by its definition: it is never a normal window. When the user makes the portal fullscreen again, forwarding continues with no new acknowledgement. While the portal is not fullscreen, the clicks on the portal display still go to neither computer by FLOW-26, also after Mission Control closes, so that a click cannot hit a window that the user did not intend (user, 2026-11-07). The user can make the portal fullscreen again with the keyboard while the portal has the focus, or end the session with the safety exit (IN-8). The session has no new state (FLOW-14). While the session waits for the confirmation, FLOW-21 keeps the portal fullscreen. The window layer reads the fullscreen state of the portal window after each event, not only after a resize event, because macOS can report the end of a fullscreen transition with no resize event after it (Claude decides, 2026-11-07).
- **UI-4** The portal shows the candidate targets, the state of the session (waiting for the verification, forwarding, ended), and the device state (confirmed, unverified, unknown; VER-6).
  - From v0.3.0, the state also shows where the user can see it while the display shows the target (user, 2026-10-27). With one display, the source is then not visible, so the target must show it:
    - The control window of each peer shows the session state and the device state: the source in a "current session" part, the target in each row of the incoming sessions.
    - Each peer has a status icon: on macOS in the menu bar (`NSStatusItem`), on Linux as a StatusNotifierItem over D-Bus (not the X11 tray). The target icon shows who controls it and the state, for example "Controlled by <source> · forwarding". The source icon shows which target it controls.
    - The icon menu opens the control window. On the target, it also has the actions of each incoming session: "Hand back", "Control from here", and "Disconnect" (Claude decides, delegated by the user, 2026-10-27).
    - A StatusNotifierItem is visible only with a host (KDE, or a bar such as waybar; GNOME needs the AppIndicator extension). Without a host, only the control window shows the state.
    - The UI redesign replaces the status icon menu with the menu of UI-9 to UI-11, and the portal shows no candidates (ACT-5).
- **UI-5** The `prompt` verifier (VER-5) shows its window on the switched display of the destination. On macOS it is a window above the fullscreen level. On Linux it is a layer-shell overlay where the compositor has it; else a normal fullscreen window.
- **UI-6** On Linux as the source, the portal is a fullscreen window. While forwarding, it inhibits compositor shortcuts (ADR 0006). It does not lock the pointer (FLOW-20). The keyboard focus is the native focus of the portal window (FLOW-22). When the portal loses it, the source sends `KeyboardAway` and applies IN-13. The shortcut inhibit is decided (user, 2026-10-27). When the portal opens, it requests the inhibit one time, so that a compositor that asks the user for permission asks then, and not after the handoff. Then it releases the inhibit, and it requests it again for the verification wait (FLOW-21) and for forwarding. If the compositor refuses, the portal shows a notice when it opens. niri asks for no permission. Not verified: whether GNOME keeps the permission after the release.
- **UI-7** The focus holder on the target (FLOW-23) is a platform capability behind an interface, so that more backends can come later. It shows nothing and does not take pointer input. On Linux it is a layer-shell surface of one pixel with exclusive keyboard interactivity and an empty input region, on the input-target output. On macOS it is a transparent Telescreen window that becomes the key window; when it is removed, the application that was frontmost before is activated again. If the target has no focus holder backend (for example GNOME, which has no layer-shell), the target accepts the session (user, 2026-10-27). It sends one desktop notification at the session start: this computer cannot hide its text cursor, so the cursor can still blink here when the source has the keyboard focus, but the keys do not come here. The row of the session in the control window shows the same warning while the session runs. Later losses of the keyboard focus give no notification. On GNOME, an app cannot place a window, keep it on top, or make an overlay; only a GNOME Shell extension can. GNOME support is a later goal (user, 2026-10-27); see section 10.
- **UI-8** A launcher shows no error output, so the start window shows what stops the start (user, 2026-11-04). It opens before the network, the capture, and the permission requests. It lists the computers of the config, and the user selects this computer. If the config is missing or not valid, the window shows the path and the problem, and has the button "Check again". If the app started with no argument and the network or a platform part cannot start, the window shows that problem. With an explicit `--config` or `--computer`, a problem goes to stderr and the exit code is not 0, as for each command.

## 7. Network and security

- **NET-1** The transport is an abstraction with a reliable ordered channel (control messages, key and button events) and an unreliable channel for the latest pointer position (ADR 0001). Key and button events must use the reliable channel.
- **NET-2** v0.1.0 uses QUIC: reliable streams for the reliable channel, datagrams for the pointer. Each pointer datagram has a sequence number. The target drops a datagram that is older than the last one that it used. The source sends a pointer datagram only if the position is different from the last datagram. It always sends one when forwarding starts and when the pointer enters the portal. A key event thus does not move the target pointer (milestone M10). The target injects only the newest position: if more than one pointer datagram waits to be handled, the target handles all of them in sequence but injects only the newest position of each session. Before the target handles the next message of the reliable channel, it handles the waiting pointer datagrams. Thus a button goes to the newest position (user, 2026-10-28; M14: a slow main loop delayed the pointer by up to 0.9 s). The source keeps at most 256 bytes of unsent pointer datagrams (about 8). If the path stops, it drops the oldest ones. No queue of pointer positions can grow without limit.
- **NET-3** Each peer has its own key pair. Both peers present a certificate, and each peer accepts the other only if its fingerprint is in the local trust list for that computer ID (ADR 0004). The user adds a fingerprint with `telescreen trust <computer-id> <fingerprint>`. No trust on first use.
- **NET-4** A peer must not accept an injection request only because the sender is on the LAN. A trusted fingerprint identifies a peer; it does not authorize it. The target refuses a session request with `NoRoute` if its config has no handoff route from that source to the device (user, 2026-10-27).
- **NET-5** The config does not hold keys, the trust list, or runtime state.
- **NET-6** Sessions have a generation number and a heartbeat. A lease is held by one session only. The local state of one peer alone must not decide the lease owner.
- **NET-7** On macOS, the network runs in the app process (ADR 0008). The app keeps `NSLocalNetworkUsageDescription` in `Info.plist`. Measured on 2026-11-04: an app that macOS starts (a launcher or `open`) gets "no answer from" on each dial until the user turns on Telescreen in the Local Network settings. The same binary started from a shell connects, because the shell is then the responsible process. A new install did not always show the request. The Local Network behavior of a new install on a different Mac is open (AC-25).
- **NET-8** Each pointer datagram has a send time: the microseconds on the monotonic clock of the source since the first pointer datagram of the session (M14). The peers do not share a clock. Thus a peer uses only the difference between two send times.
- **NET-9** The target records statistics of the pointer datagrams of each incoming session (M14). The statistics do not change the session.
  - Counts: received datagrams, used datagrams, late datagrams (dropped by NET-2), lost datagrams (sequence numbers between the first and the newest used one that did not arrive).
  - The send interval: the difference of the send times of two datagrams with consecutive sequence numbers.
  - The arrival interval: the time between the arrivals of two consecutive used datagrams.
  - A pause: an interval with a send-time difference of more than 100 ms (the pointer did not move). A pause is counted, and its interval is not in the interval statistics.
  - The arrival time is the time when the network thread receives the datagram, not the time when the main loop handles it.
  - The delay variation: for each received datagram, its arrival time minus its send time, minus the smallest such value of the session. It is not the one-way latency, because the peers do not share a clock.
  - The handling delay: for each received datagram, the time from its arrival to the time when the main loop handles it.
  - Injected datagrams: the used datagrams that the target injected (NET-2: the others had a newer datagram in the same batch).
  - Each interval, the delay variation, and the handling delay give p50, p95, p99, and the maximum (nearest rank).
  - Each series keeps its newest 65536 samples. The counts are for the whole session. The memory of the statistics does not grow with the session time.
  - The target writes a summary to the log when the session ends. The debug protocol returns the summary of the current session, else of the last session.
- **NET-10** A dial that fails does not retry automatically. The menu and the main window show a candidate with no connection as "offline", and a candidate with a running dial as "connecting". Each display section has a "Refresh" button at the right of its title (UI-18). The button always shows: it does not go away after a click (user, 2026-11-07). It is disabled when each candidate of the display with no connection has a running dial or search, and when all candidates of the display have a connection (Claude decides, 2026-11-07). It dials each offline candidate of the display one time. It does not run `portal-match` again, and it does not start a handoff (user, 2026-11-05).
- **NET-11** One computer can have more than one address (user, 2026-11-05). `endpoint.host` is one host or a list of hosts, and each host is an IP address or a DNS name. A dial tries all known addresses of the peer. It starts the first address, and it starts each next address 250 ms later. It uses the first IPv4 address of each host. The first QUIC handshake that completes wins. Only the winner sends `Hello`, and the transport closes the other attempts. Thus a losing attempt never replaces the connection (the listener registers a connection only after `Hello`). A new address for a peer with a running dial joins that race. If all attempts fail, the failure gives the reason of each address.
- **NET-12** Discovery finds the address of a trusted peer with the mDNS responder of the system (ADR 0011, user, 2026-11-05). macOS uses Bonjour. Linux uses Avahi through D-Bus. Telescreen has no responder of its own. If the system has no responder, discovery is not available, a notice gives the cause, and dials to the configured hosts still work.
- **NET-13** Discovery is on for a computer only if its config section has `endpoint.discovery: mdns`. A computer with this key can omit `endpoint.host`. A discovery result is only a hint for an address. It does not identify a peer: the mutual TLS check of NET-3 identifies the peer.
- **NET-14** "Allow discovery" in the control window makes this computer discoverable for 10 minutes (user, 2026-11-05). The control window shows the button only if the section of this computer has `endpoint.discovery: mdns`, and it shows the remaining time. The user can stop it before the end. A new start of the app does not continue it. The computer registers one service of type `_telescreen._udp` with a random instance name, the port of its endpoint, and its fingerprint as the TXT key `fp`. The record has the host name of the computer, because the system responder adds it (measured on 2026-11-05).
- **NET-15** Each dial of the portal candidates starts a search if a candidate with no connection has `endpoint.discovery: mdns` (user, 2026-11-05): when the portal finds its device, and when the user selects "Refresh" (NET-10). The dial and the search run at the same time, and the first address that connects wins. A search runs for 30 seconds, and it ends when no such candidate remains. A candidate with a running search and no running dial shows "searching". The search sends no fingerprint. A candidate with no configured host and no known address has no dial.
- **NET-16** Telescreen uses a search result only if its `fp` is in the trust list, and only its private IPv4 addresses (RFC 1918 and link-local). Each computer that the trust list holds for this fingerprint gets the addresses. A new result replaces the previous result of that computer. The results are in memory only. A dial tries the found addresses first, then the configured hosts. A result for an offline candidate starts a dial. If a dial to this candidate runs, the found addresses join its race (NET-11).

### 8.3 Distribution

- **DIST-1** v0.1.0 is built from source: a script makes an ad-hoc signed `Telescreen.app` on macOS, and `cargo install` on Linux.
- **DIST-3** v0.3.0 is the first binary release (user, 2026-11-04). A pull request from `main` to `release` runs the checks `linux` and `macos`, and they are required to merge it. `main` has no checks (user, 2026-11-05). The merge is a push to the `release` branch, and it runs `.github/workflows/release.yml`. It makes a GitHub release with `v<version>` from `Cargo.toml`: an archive for macOS arm64, an archive for Linux x86_64, `sha256sums.txt`, `install.sh`, and a `PKGBUILD`. The user installs with `install.sh`, with no sudo. The `PKGBUILD` is not published to the AUR. The macOS app has the self-signed "Telescreen Dev" signature if the secrets exist, else an ad-hoc signature. It is not notarized, so a download with a browser is blocked by Gatekeeper.
- **DIST-4** The Linux archive has a stripped binary and the launcher entry `dev.telescreen.Telescreen.desktop` (user, 2026-11-04). The file name is the Wayland app ID of the windows, so that a compositor can link a window to the entry. `install.sh` installs the entry in `~/.local/share/applications` with the absolute path of the binary, because the session of a launcher can have no `~/.local/bin` in its `PATH`. The `PKGBUILD` installs it in `/usr/share/applications`. The entry has the icon `dev.telescreen.Telescreen`: the archive has it as a 256 x 256 PNG, `install.sh` installs it in `~/.local/share/icons/hicolor/256x256/apps`, and the `PKGBUILD` in `/usr/share/icons/hicolor/256x256/apps`. The Qt windows also set the icon at runtime, for a start with no installed entry (Qt 6.8 or newer, with xdg-toplevel-icon; user, 2026-11-08). The binary links the Qt of the system (step g1), so the `PKGBUILD` depends on `qt6-base`, `qt6-declarative`, `qt6-wayland`, `kirigami`, and `qqc2-desktop-style` (Claude decides, 2026-11-08).
- **DIST-5** `scripts/make-macos-app.sh` does not put a local build in `target/` (user, 2026-11-04), because the launcher then shows two Telescreen apps. The default output is `~/Library/Caches/telescreen-dev.noindex`. Spotlight does not index a `.noindex` directory.
- **DIST-2** Before a binary release: test the real download path (dmg with quarantine, Gatekeeper, App Translocation) and each signing type that you ship (`docs/spikes.md`, spike 4).

Each row must pass on each environment in the support matrix before you mark a version complete.

| ID | Scenario | Expected |
| --- | --- | --- |

| AC-2 | Two Linux computers share a second display. The Mac does not connect to it | The Mac is not a candidate for the second device |

| AC-15 | "Hand back" in the session row of a portal on the source | The session of that portal ends. Local input comes back. The target runs its route back, and the source shows the prompt (HB-3) |

## 10. Open questions

- GNOME as the target (user, 2026-10-27: GNOME must be supported in the end). GNOME has no layer-shell, so the prompt (UI-5) and the focus holder (UI-7) need a different backend behind the same interfaces. A candidate is a GNOME Shell extension. X11 is not an option (user, 2026-10-27).

- The lease arbitration and the recovery protocol (NET-6): message design and timeouts. Tentative proposal for v0.1.0: `docs/adr/0007-session-protocol.md`. The user decided to keep it tentative until the hardware tests (AC-18) run.
- Which special shortcuts to support beyond IN-5, and the per-platform list of shortcuts that cannot be captured.
- The effect of Wi-Fi delay spikes (spike 4: p99 about 85 ms) on the pointer in real use. Measure it in the product.
- Minimum OS versions for each package. macOS: 27.0 for v0.1.0, the only tested version (user, 2026-10-27). Linux: open.
- Drivers for the output format of one tool (for example `betterDisplay` or `ddcutil`, with `expect`): a later version, after their output is measured on the hardware (user, 2026-10-27). The other driver decisions are in `docs/config.md`.
- UI redesign (section 4.7, ADR 0012):
  - A key test with the user that the inhibit of a cxx-qt window blocks a compositor shortcut (spike 6 saw only the `active` event).
- Login screen control (a memo, not planned; user, 2026-11-06). Example: the Linux computer shows SDDM, and no user session runs. A system service that starts before the login can inject keys through uinput, because uinput is in the kernel and the greeter reads it through libinput. Limits: the service is not a client of the greeter compositor, so it does not know the output geometry, and the absolute pointer position is approximate; no clipboard; no `prompt` verifier. Open: the handover between the system service and the app of the user session (port, identity, trust keys), and the security of remote keys at a password field. A decision needs its own ADR.

Decisions of the implementation (Claude, 2026-10-27). The user confirmed the items that name the user:

- The texts of the session end on the source (user, 2026-10-27), with the target label:
  - `TargetStopped` ("Disconnect" on the target): "<target> disconnected the session".
  - `TargetDisconnected` (the target app quit and told the source): "Telescreen quit on <target>".
  - `PeerLost` (heartbeat timeout or a closed connection): "Connection to <target> lost".
- "Control from here" (FLOW-17) needs a device match for the display (user, 2026-10-27). If no device matches, the target shows a notice, does not start a handoff, and the old session continues.
- CLIP-8: v0.2.0 uses only `zwlr-data-control-unstable-v1`. `ext-data-control-v1` needs a staging feature of `wayland-protocols` and can come later.
- The Linux clipboard backend reads an offer for at most 1 second. A text larger than 256 KiB is cut to its longest valid UTF-8 prefix, so that the core rejects it as too large (CLIP-6).
- The controller does not read the clipboard while the switch is off or while no session can sync (CLIP-2). On Linux, the data-control connection is open only while the switch is on and a session is in forwarding (user, 2026-10-27). At start, the app only checks that the compositor has data-control (CLIP-8). When the connection opens, the current selection is the old text of CLIP-3. When the connection closes, Wayland removes a text that Telescreen still provides (CLIP-11).
- Later goal: no stable identity on the network (user, 2026-11-05). See ADR 0011, "Later goal".
